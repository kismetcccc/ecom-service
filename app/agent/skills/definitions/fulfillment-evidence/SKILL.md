## 履约证据核对 SOP

目标是解释已知记录与缺口，不是在缺少实时证据时猜测异常原因。

1. 明确当前用户要查的一个订单；缺失时请用户提供，不能从历史猜测。
2. 使用 query_order 和 query_logistics 查询同一订单。保留原始工具记录，不把自己的总结当作证据。
3. 先核对订单号和运单号；不匹配时停止合并。查询失败只说明哪个环节缺失。
4. 区分不同维度：退款处理中 + 运输中可以共存，不等于已到账、已拦截；订单与物流签收状态不同可能是同步延迟，不等于丢件。
5. 用户表示没收到是用户报告，物流显示签收是系统记录；两者构成待核实争议，不能裁定责任。建议核对签收凭证，不声称已联系承运商。
6. demo/demo_seed 是演示数据。不能用演示日期推导真实延误天数；系统快照也不能证明承运商实时情况。无政策依据时不能承诺时效、赔偿或自动退款。
7. 只有涉及具体政策规则才调用 search_knowledge。检索失败不能抹去订单记录，也不能继续编造政策。

## 输出模板

- 已核实：订单和物流记录，以及数据是否为演示。
- 差异/缺口：哪些维度不同，缺少什么证据。
- 下一步：需要用户补充的信息或人工应核实的记录。

保持简短，不输出地址、电话等私人信息。不执行写操作。

## 可执行验收

运行时对本轮工具证据执行固定 Python 校验器 fulfillment_audit.py，生成带证据编号、SOP 哈希及规则版本的 skill_audit。校验器不会执行本文中的任意代码，不请求模型，也不调用业务写接口。它只核对覆盖的规则，不能认证答复整体正确，也不能证明真实延误原因。独立回复质检仍负责审核生成文字。
